# AI Game Platform

Research and planning for a community-driven platform where users describe a 2D or platformer game, optionally referencing existing games for style, and an AI harness builds a playable, remixable browser game that other people can play and test.

## Contents

- `docs/system-plan.md` — the full system plan: product shape, model-agnostic quality strategy, architecture, monorepo layout, genre template contract, harness directory, generation state machine, data model, bundle contract, phased build plan and tracked risks.
- `docs/2D AI game creation harness.md` — the main research report: reference games and what makes them high quality, the style-reference feature design, the recommended harness architecture (engine, skills, templates, asset pipeline, verification, multiplayer, sandboxing, cost), and a phased build plan.
- `docs/research_notes/` — the underlying research notes the report was synthesized from:
  - `reference_games_and_quality.md` — the 2D reference canon, art taxonomy, and game-feel constants
  - `engines_and_multiplayer.md` — browser engine comparison, multiplayer patterns, sandboxing, agent testing
  - `harness_architecture.md` — how existing AI game tools work, relevant research, coding-agent harness patterns, cost
  - `asset_pipeline.md` — sprite, animation, tileset, audio and font generation tools and the de-AI cleanup pass
  - `reference_feature_legal_quality.md` — legal boundaries for "in the style of", storefront policies, ownership, automated quality metrics
  - `model_agnostic_quality.md` — evidence on producing frontier-quality output on cheap or open-weight models: verifier-driven sampling, structured outputs, curated knowledge, prompt optimization, distillation, multi-agent patterns, open models and harnesses

## Repository layout

- `packages/schemas` — zod schemas for every artifact: style card, systems, GDD front matter, levels, behaviour FSM and ECA rules, waves, playtest and gate reports, bundle manifest, bridge messages, model policy, trajectory, create/edit requests and the edit route.
- `packages/sdk` — the runtime: a deterministic pure-TypeScript simulation (seeded RNG, event bus, tilemap physics with runtime tile changes for doors, FSM/ECA interpreters, `defineSystem`) plus a Phaser 4 view, manual/realtime drivers, the test seam (`window.__game`, `window.__TEST__`) and the iframe bridge guest. A game draws its cast with its own sprite designs when it has them (`content/sprites.json`: for each type a shipped sprite of the same build to start from, its own colours for the art kit's ramps and a few pixel overlays that move with the body), each compiled on its own: one that cannot be drawn falls back to the shipped sprite, never to a placeholder or a crash, and the test seam counts what fell back. Larger characters are drawn from rigs (`render/art/rig`): parts on a skeleton, posed by keyframed clips, shaded in the game's palette with ordered dither, an outline and a normal map per frame, cloth that swings on its own (verlet chains), smears on the frames that hit, and the floor hiding what dips below the feet; the art QA (`checkRig` in `packages/validators`) holds every frame to the palette, a full outline, no lone pixels, few jaggies, its anchor and no pops, and the golden lock pins every frame. Combat is frame data the sim and the drawing both follow (`sim/moves.ts`): a game's moves (`content/moves.json`, a `MoveSet` held to `validateMoves`, every foe's blow winding up for 150 ms or more) wind up, hit for their active ticks with boxes that strike each target once, and recover; a blow throws back, staggers (`Entity.stunTicks`: the foe's behaviour holds) and holds the world still a moment (`World.hitstop`) unless the foe's poise holds; and the view draws a move's clip by the move's clock, so the frame with the blade's arc is on screen exactly while the move strikes.
- `packages/engine` — builds the shared engine chunk (Phaser + SDK) that every game bundle treats as externals; syncs Phaser's agent skills into the harness.
- `packages/validators` — pure checks: level solver (BFS over the feel preset's jump envelope, with air jumps, a dash and exact air speed for ability-gated genres), behaviour structure, GDD front matter and sections, systems against the catalog, juice lint over a playtest event log, parameter impact, and art QA for sprite designs (a base of the type's build and kind, overlays inside the frame and on animations the base has, no redraw of more than two thirds of a frame, no pixels apart from the body, no recolour that changes nothing, nothing melting into an unoutlined floor, no foe in the colours the player is known by, no two types alike; every shipped sprite and every genre's cast as it ships pass).
- `packages/template-core` and `packages/templates` — the genre contract (`GenreManifest`), shared systems (pickups, top-down movement, wave spawner, survival timer, arena validators), the blocks only freeform games compose, which bring their own entities, level dressing and proving bot (`carry`: the key picks up cargo lying about or a source's next item and hands it over at a dropoff, a hit knocks it down, and the stations are placed on every level, on solid footing within a screen top-down, on the path side view, both ways reachable; its courier bot plays the job; `orders`: dropoffs ask for a delivery in turn and wait, and a walkout costs health, tighter on harder levels; both are drawn with what is held over the head, a bubble of time left over each order and a pointer to one off the screen), the conformance check a game's own systems are held to (each does what its contract in `design/mechanics.json` says and nothing more, saves and loads, shares no state between two runs, and keeps to its time budget; run by the game's own test) and the genre packages: `genres/platformer` (Celeste-class feel, chunk-grammar levels, walker/hopper/turret FSMs, walker and chaos bots, and for freeform games a runner: `auto-run` keeps the player running right at a pace of the feel's top speed that can rise each minute, takes over left and right (the play page and the explorer leave them out), and its levels are as long as it runs in the GDD's level time), `genres/survivors` (top-down arena, auto-attack with level-ups, wave spawner, kiter/afk/chaos bots, DPS-vs-pressure wave validation) `genres/topdown-action` (rooms joined by doors, directional melee with aim assist, telegraphed enemy bites, archers, the exit locked until the floor is clear, a path-finding clearer bot as solver) `genres/shmup` (one-screen sky, waves from the top, hold-to-fire shots, aimed bullets, drones that weave and tanks that grind, a trajectory-scoring dodger bot as solver; its shooter also aims for a freeform game: where the player faces, forward or up in a side view, or at the nearest foe in range, and its shots turn along their flight) and `genres/metroidvania` (one cavern per level with ability gates: wings behind the start for a double jump, a cliff only it clears, a key on a pillar, a locked door that opens at runtime, boots for the dash and a spike pit that needs both; an ability-gated reachability search as validator and a planning seeker bot as solver, while the greedy walker must fail) and `genres/puzzle` (Sokoban-class boards: one tile per step, one crate pushed at a time, free undo and restart; a push-optimal A* solver with dead-cell and 2x2-freeze pruning and a step budget is the validator, boards are generated by reverse play from the solved position and ramp by the fewest pushes they need, and the solver bot plays the plan in the real sim) and `genres/lifesim` (a Stardew-class farm: a day clock from six to two, energy, soil to till, sow and water, crops that grow overnight (written from the player's idea after the systems, `content/crops.json`, and held to the season's rules: every crop ripens and pays, none is worse than another in every way, the field reads at a glance), a seed shop and a shipping bin that pays overnight through in-game menus, a bed to end the day, and a season won by the purse; the farm grammar lays out a fenced one-screen farm whose field grows with difficulty, the quota is a share of what an ideal season earns with the game's own crops and rules, and a farmer bot that plays by the same book proves every season) and `genres/castle` (the first genre of the castle tier: 16 px tiles, a hero 14x42 drawn larger, a 480x270 view, its own agile and weighty feels and budgets; a level is a region of rooms, a screen each, on a grid (`LevelJson.rooms`): doorways join neighbours on a row and a shaft of one-way ledges joins the rows; the `rooms` system wakes the room the player enters and puts the others to sleep, and the `rest` system saves at an altar (health back, the checkpoint there, a `ProgressSave`) and loads the region again from it: enemies back, what was found and opened kept, the player at the altar. A fall does the same from the last rest, keeping what was found since. The reload happens inside the sim (`ctx.reloadFrom`), so the run goes on through it (the tick, the input log, the rng, the score) and one script from the region's start replays every rest and every fall. Meanwhile `abilities` keeps the relics' abilities as props so they last through that and into the next region. The generator lays the way along the top row (the wings behind the start, halls, an altar, a 4-tile ledge only the wings climb, the boots), then down a shaft to the second altar and back along the row below to the way out under the first altar, past a 10-tile chasm only the double jump with the dash crosses (both gates sized to hold under both feels); from the way out a shaft of ledges climbs to an iron grate in the first altar's floor, which a head opens from below for good (the `shortcuts` system): a shortcut loop, the wings climbing back to the rest and a fall dropping to the way out. The world solver checks the relics in order reach the goal, nothing the player can get to strands them, every room is reached and no stretch between rests runs past four rooms (measured as built, the grate shut), and counts a gate as a loop only when, once opened, it joins its rooms both ways with a rest on one side; its route bot, which rests at every altar it passes, is the solver: it plans its way over the jump graph (less the arcs that would come down through a floor, and with two tiles of reach to spare where the region allows it) and follows it, jumping where a planned jump leaves the ground and taking the air jump and the dash where the planned jump needs them. The hero fights with a sword whose moves are data (`content/moves.json`, which every castle game ships and the `combat` system reads): on the ground a chain of three cuts, each pressed in the last one's window (or just before it), in the air an overhead cut, and with down a plunge that bounces off what it strikes; a cut roots the hero but for its own step, which stops at a ledge, and a dash cuts it short late in it; a blow throws the hero back, reeling (less long in the air, so a hit over a pit is a scare, not a fall). The guard key parries (a parryable blow in its 8-tick window is turned, the foe reeling, open to a riposte on the attack key), the item key drinks a flask (hearts back unless a blow spills it; three, full again at every rest), and once the boots are found a dash slips every blow. Foes take cuts to fell, and fight back with moves of their own, started by their behaviour playing the move's clip (the ghoul's claw, the hound's pounce, the gargoyle's spit, the sentinel's spear thrust, the wraith's hex, the bone archer's arrow), each winding up long enough to read: the view flashes a foe over its wind-up, and a cut in it breaks the attack off; the behaviour lint holds a state that makes a move to standing still for it and waiting it out, and on the ground a move moves its body only through its motion. A move's i-frames keep every blow off its body (the wraith's fade, drifting it through the hero unseen), and a cut strikes shots out of the air. The sentinel's shield turns aside blows from the front (a clang, sparks, the hero thrown back unhurt) until three cuts break its guard; over its head, at its back, or once its own thrust swings the shield open, blows land. From difficulty 0.2 the headsman waits in a boss room before the way out: it rises from its knee, untouchable, under a title card with its name, and the `arena` system shuts the room's doorways behind the hero until it falls (a fall in the arena opens them, the last rest bringing the boss back whole; once beaten it stays beaten). It chops (parryable), leaps at a hero who keeps away and brings its cleaver down as it lands, drags a wave of sparks along the floor, and at half health roars into a faster fury with a two-blow combo; its poise shrugs off cuts until two chains or a riposte break it. The world solver warns when the way out does not lie behind the boss's room (`boss_bypassed`), and a region of a one-level castle game grows with the tier (difficulty 0.3, 0.5 or 0.75: more halls, the later foes). The route bot cuts down the foes in its way, waiting on solid ground for one coming over a pit, baits a raised shield (in to the edge of the thrust's reach, back out as it winds up, in to cut as it recovers), parries any parryable blow that will reach it and ripostes, cuts the boss only in its openings (reeling, or recovering from a blow), slips under its leap with the dash, jumps low shots and the boss's wave and cuts the others out of the air. It sees every wind-up at once and parries on the tick; the same bot played as a person would (`human`: a wind-up, a shot or a reeling foe registers 12 ticks late, and each parry is up to 4 ticks off) is the genre's fair bot, which every level must also fall to (the level oracle, the levels stage, the level editor and the scaffolded game's own test), so a fight only a frame-perfect bot can win fails the gate (a boss whose chop winds up in 12 ticks does). A masher (`chaos`, the sword's keys pressed at random) and a player standing still never beat the boss, and the rubric reads the shortest wind-up from the game's moves and plays each region standing still. Its games are drawn in a setting of their own: cut stone laid in courses, worn bright where it is walked and dark deep in the wall, in front of the painter's backdrop in the theme nearest the game's palette; the hero is the knight's rig (idle, run, jump, fall, dash, hurt, the three-hit chain, the air cut and the plunge), and its cast (a skull-faced ghoul that shambles and lurches, a crypt hound that crouches, runs and leaps, a stone gargoyle that wakes to spit, a sentinel in crimson plate behind a tower shield with a spear over its rim, a hooded wraith trailing ghost-fire that dissolves as it fades, a bone archer in a torn crimson cowl, the headsman in a spiked iron helm with ember eyes behind its grille, a crimson tabard and a rust-edged cleaver (168x112 frames), the altar's font and flame, the souls, the shortcut's grate) is drawn by the same rasterizer and light, then baked into ordinary recipe templates, so it takes the game's palette and outline and goes through the same art QA; enemies keep to the room they start in; the view is held to the room the player is in and slides to the next, at a whole-number scale of 480x270 (a genre's `styleDefaults` set its starting view, palette and frame rates). It is not a freeform base yet (`FREEFORM_BASES`), so freeform's schemas and prompts are unchanged). Adding a genre is one entry in `packages/templates/src/node.ts` and one in `src/check.ts`, plus the package in the templates, game-base and web dependency lists. Each genre also exports a browser-safe check kit (its validator, bots and solver); `@gg/templates/check` collects them so the level editor runs the gate's own check in the page.
- `packages/game-base` — the dependency set every scaffolded game links against, so a game outside the workspace still builds and tests.
- `tools/scaffold` — `gg-scaffold`: emits a complete game package from a GDD, systems.json and style card; every placeholder level passes the validator and the genre's solver bot.
- `packages/bots` — Playwright smoke (ready flag, zero console errors, manual vs realtime vs in-page replay hash), contact sheets, a static server.
- `packages/llm` — provider clients (Anthropic, OpenAI-compatible), pricing, and the sample → verify → repair → select loop for schema-constrained artifacts.
- `packages/db` — the `Store` interface (games, versions, jobs, events, trajectories, policies, objects, remix forks with lineage, and the community layer: plays, one-tag ratings, per-player ranking, publishing to the feed, a rewarded test queue with credits, moderation: player reports, suspension at three reporters, moderator resolutions, takedowns (the bundle files go to a private quarantine) and strikes, appeals and DMCA counter-notices with reinstatement, play events for the creator's heatmaps: deaths, quit points and position samples, aggregated per tile for the owner, training pairs for distillation, never stored for anyone who opted out, and jams: themed events whose entries are frozen at the version entered and whose votes need a play of it) with a Supabase implementation and a JSON file store for local runs. `supabase/migrations/0001_core.sql`, `0003_community.sql`, `0004_moderation.sql`, `0005_play_events.sql`, `0006_appeals.sql`, `0007_training_pairs.sql`, `0008_jams.sql`, `0009_freeform.sql` and `0010_level_proofs.sql` (players' winning runs on levels no bot won, and listing that waits for them) are the schema; 0004 also limits what a signed-in client can write directly (state, listing, heads, credits and the moderator flag change only through the functions). `ranking.ts` holds the rank formula, the moderation thresholds and the jam rules and standings; the migration test runs the migrations on an embedded Postgres (PGlite) with Supabase's API roles and default grants, checks SQL and TypeScript rank the same rows the same way, and checks the client privileges.
- `packages/assets` — the asset pipeline's core: image providers (an image model behind a key, or the procedural painter that needs none: moonlit gothic ruins, a sunlit coral reef, a frozen clockwork city, each in far, middle and near layers; the painter lives in the SDK's art kit, so a game's view paints the same backdrops), putting an image on the game's pixel grid and palette and making a layer wrap, and the backdrop QA (on the palette, drawn at the game's pixel size, the far layer opaque, wrapping cleanly); a provider whose image fails falls back to the painter.
- `packages/catalog` — the style reference feature's boundary: curated cards of unprotectable attributes for named games (palette mood, pixel density, outline rule, animation feel, camera, typography class, audio mood), a resolver for free-text titles and for the games an idea cites ("like Blasphemous", "Hades-like"), a merge into the style card, and a sanitiser so titles (the catalog's and any other a request names) and blocked terms (characters, places, studios) never reach a prompt or a bundle, while ordinary words a game also uses as names ("knight", "survivors") stay in the idea.
- `packages/config` — eslint preset with the GlueTS rules for simulation code, tsconfig presets, the game vite config.
- `samples/platformer` ("First Steps"), `samples/survivors` ("Last Light"), `samples/topdown-action` ("Ember Halls"), `samples/shmup` ("Static Sky"), `samples/metroidvania` ("Undervault"), `samples/puzzle` ("Crate Cellar"), `samples/lifesim` ("Willowbrook Farm", with crops of its own) and `samples/castle` ("The Salt Chapel", a region of thirteen rooms with two altars, and the route bot's run through it) — hand-tuned golden games built from the template systems plus data.
- `harness/` — the per-job Claude Code project: `AGENTS.md`, path-scoped rules, subagents, hooks, the worker-runnable gate, per-stage presets (`stages.json`), budgets, and skills with bundled scripts (gdd-author, systems-select, mechanic-author, behaviour-author, level-design, asset-prompting, playtest, juice-pass, regression, budget-check, edit-apply, playbook, verify).
- `workers/generator` — the job state machine: create plan (GDD → systems → sprites → scaffold → behaviour → implement → levels → integrate → playtest → juice → review → budget → publish) and edit routes (parameter, style, behaviour, content, code, plus authored content from the level editor, which skips the router and is written only after the validator and the solver bot accept it); runners for Claude Agent SDK sessions, a built-in guarded tool loop for open-weight and OpenAI-compatible models (same AGENTS.md, skills, playbook, path and command guards as code, scrubbed context), structured calls and worker-implemented stages; worker-owned gates, checkpoints, trajectories (every attempt's gate report is kept), the publisher; a fake provider for dry runs without keys. When a job finishes with every gate passed, the model-written artifacts of its stages (GDD front matter and body, systems, behaviour FSMs, structured artifacts, the edit route) become training pairs against the stage's first prompt; fallbacks, dry runs and anyone who opted out (the requester, the game's owner or the owner of a game it was remixed from) are left out. The sprites stage gives the cast its own look from the idea in one structured call (each type's allowed bases are shown as pixel rows), held to the art QA in the game's palette; everything the QA finds goes back as a repair, and when no answer passes the designs that hold are kept and the rest draw as they ship.
- `apps/web` — Next.js app: the home page is the ranked feed (listed games whose gates passed and that players have not marked broken); the play page records each session (active seconds, levels finished, deaths, and where the player died, spent time and quit; sent on pagehide) and takes a one-tag rating; a game that rests (the castle's altars) leaves a save in the player's browser at each rest (the bridge's `save` message, a `SaveBlob` of the level and the `ProgressSave` in it), and the play page offers Continue, which starts the game again from it (the init's `save`; a run picked up there sends no proof, as it did not start at the level's start); the test queue page lets a player claim an unreleased game, play it 30 s, report works or broken and earn credits; players report a game from the play page (ip, abuse, broken, other) and moderators work the `/moderation` queue (dismiss, unlist until fixed, warn, licence an ip claim, remove); a suspended game is hidden from everyone but its owner and moderators, a removed one from everyone, and neither can be remixed. The owner of a removed game appeals from its workspace (a counter-notice with consent to jurisdiction for an ip takedown, which moderators can reinstate 14 days later; a plain appeal otherwise), and moderators reinstate or uphold from the appeals queue. Locally a header switcher sets the acting user (`moderator` is the file store's moderator). Jams (`/jams`): moderators set a theme and when entries open, submissions close and voting closes; owners enter one listed game made after the start (for a remix, its original too), frozen at the version entered; players who played an entry 30 s score it 1-5 on fun, theme and look, never their own; results rank entries with 3+ votes by a score that counts three extra votes of 3 per criterion, and leave out entries taken out of the feed. The create page and the games list carry the player's training consent: unchecking it opts all their games and remixes of them out and deletes what was recorded. Also the create form (with style references), games list, the creator workspace (job progress, playable preview in a sandboxed iframe over the bridge, evidence panel, edit chat, parameter tuning panel, style card editor and a tile/entity level editor that send deterministic edits, remix, and a community panel to publish to the feed and ask for testers; the level editor can overlay other players' deaths, quit points and time spent on each tile), the play page with a remix button. The workspace is the owner's (moderators may look in; anyone else lands on the play page), since its jobs carry prompts, edit messages and private style references; its code view lists a version's source from the checkpoint (systems, levels and behaviour data, design files, tests, config; never the private concept, an edit request, provenance, build output or reports), marks what changed since the version it was built on with a line diff, and "Ask for a change" starts an edit about a file. The create page's last card, "Anything else", takes any idea as a freeform game: the workspace lists its own plan (the cast after the systems, the winning runs recorded again after the code), its pill names the genre it builds on, and its play page lists the keys its own systems use (the publisher writes each version's controls from its systems, the values it gives them and its own systems' contracts). A game is listed, and in the feed, only once every level of its head has a recorded winning run: a freeform level no bot could win ships without one, the workspace's evidence names who won each level (a bot or a player) and the community panel which levels wait, and the play page and the test desk ask players to finish them. Before a level waits, the worker gives the search a way through: where the explorer lost its way (a maze, a long walk round), the model writes the level's hints from its rows, its goal and where the search got stuck, with the floor's own walk as a start (`content/hints/<level>.json`: up to twelve steps in order, a tile to reach or a HUD number to get to), and the explorer climbs them one at a time; hints that find the win are kept beside the run, the rest are dropped. Where a game's own systems change how its levels are won, no bot of the platform's knows the way: once its levels are made, a `bot` stage (an agent session with the bot-author skill, passed over when no level waits) writes a bot of the game's own in `src/bots`, which the game's prover plays after the solver and before the explorer, getting about with the courier's way of walking and jumping (`goToward` in `@gg/template-core`). When a player wins such a level, the game sends the run over the bridge, the page posts it, and a worker replays it on that version (job kind `verify_proof`): a run that wins proves the level for everyone, one that does not is kept with the reason, and the edits that follow keep the run while it still wins. The level editor checks a level in the browser with the genre's validator and solver bot before it can be applied; dev and build run on webpack so the shared TypeScript packages resolve.
- `tools/evals` — the benchmark: 46 prompts across the eight curated genres, 16 freeform ideas and 3 reference-tier ideas on the castle (`--tier R`, graded by the castle rubric in `src/rubric.ts`: the bar Track R aims at, line by line, from the hero's size to boss phases, rooms, people to talk to, endings and music, each measured from what the game is made of or reported as not yet measurable), dry or live runs per policy, pass^k and per-stage rates, cost per passing game; policy files for the frontier path, the first cheap experiment (Haiku with k-sampling) and an open-weight policy through the built-in open runner. `pnpm gap` is the mechanic-gap report: 60 game ideas as players pitch them (`ideas.json`), each labelled with the mechanics it needs, against what the systems catalog covers: how many it builds whole, what each missing mechanic is asked for, and the order to build them in (the one that makes the most ideas whole next).
- `tools/playbook` — distils playbook candidates from stored trajectories (a stage that failed its gate then passed, with the failing checks and the passing summary); `promote` appends a verified lesson to the genre's playbook with its source.
- `tools/distill` — `pnpm distill status` counts verified pairs per stage against the 2,000 unique inputs a LoRA run needs; `pnpm distill export` writes chat-format `train.jsonl` and `holdout.jsonl` per stage (one pair per input, the split fixed by the input so nothing moves from holdout to train between runs, games under moderation left out) with a manifest of file hashes, pair ids, models and the artifacts' JSON Schemas, and stamps the pairs it exported. Exports hold user prompts and go to the git-ignored `.gg-distill/`.
- `tools/demo` — `pnpm demo` runs the sample through the whole gate, then a dry-run create job through publish, then an authored level edit (a coin on the spawn tile) through apply-content, playtest and publish, and prints the evidence bundle.

## Running it

```
pnpm install
pnpm typecheck && pnpm lint && pnpm test
pnpm demo                       # engine + sample gate + a dry-run create job through publish
pnpm bench --limit 2 --k 1      # one prompt per genre through the pipeline (dry)
pnpm distill status             # verified training pairs per stage (live runs record them; dry runs do not)
pnpm distill export --new-only  # chat-format JSONL per stage in .gg-distill/

# create a game from the CLI (dry run needs no key; drop --dry-run with ANTHROPIC_API_KEY set)
pnpm --filter @gg/worker-generator exec node --import tsx src/cli.ts create --prompt "..." --genre platformer --dry-run
pnpm --filter @gg/worker-generator start -- --once

# apply levels authored outside the model (what the level editor sends): { "levels": [LevelJson, ...] }
pnpm --filter @gg/worker-generator exec node --import tsx src/cli.ts edit <gameId> --message "edited l01" --content levels.json --dry-run

# the web app (reads the same local store; run a worker alongside it)
pnpm --filter @gg/web dev      # http://localhost:3000 (feed), /create, /test (test queue)
```

## Key decisions so far

- Web app first; a desktop wrapper (Tauri) only later for a Steam listing.
- 2D and platformer games only for the first version, with a platformer and a survivors-like as the initial vertical slice.
- Phaser 4 in a thin platform SDK as the fixed runtime; Colyseus for multiplayer; games sandboxed in opaque-origin iframes.
- Named game references resolve to a visible style card of unprotectable attributes; characters, names, logos, layouts and music are blocked.
- Quality must not depend on the model: the model emits data under small schemas and restricted glue code, never engine API calls; every stage samples, verifies, selects and escalates; knowledge is curated from verified runs; a second runner (OpenCode) carries open-weight models.
