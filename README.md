# AI Game Platform

Research and planning for a community-driven platform where users describe a 2D or platformer game, optionally referencing existing games for style, and an AI harness builds a playable, remixable browser game that other people can play and test.

## Contents

- `docs/system-plan.md` — the full system plan: product shape, model-agnostic quality strategy, architecture, monorepo layout, genre template contract, harness directory, generation state machine, data model, bundle contract, phased build plan and tracked risks.
- `docs/2D AI game creation harness.md` — the main research report: reference games and what makes them high quality, the style-reference feature design, the recommended harness architecture (engine, skills, templates, asset pipeline, verification, multiplayer, sandboxing, cost), and a phased build plan.
- `docs/research_notes/` — the underlying research notes the report was synthesized from:
  - `reference_games_and_quality.md` — the 2D reference canon, art taxonomy, and game-feel constants
  - `engines_and_multiplayer.md` — browser engine comparison, multiplayer patterns, sandboxing, agent testing
  - `harness_architecture.md` — how existing AI game tools work, relevant research, coding-agent harness patterns, cost
  - `asset_pipeline.md` — sprite, animation, tileset, audio and font generation tools and the de-AI cleanup pass
  - `reference_feature_legal_quality.md` — legal boundaries for "in the style of", storefront policies, ownership, automated quality metrics
  - `model_agnostic_quality.md` — evidence on producing frontier-quality output on cheap or open-weight models: verifier-driven sampling, structured outputs, curated knowledge, prompt optimization, distillation, multi-agent patterns, open models and harnesses

## Repository layout

- `packages/schemas` — zod schemas for every artifact: style card, systems, GDD front matter, levels, behaviour FSM and ECA rules, waves, playtest and gate reports, bundle manifest, bridge messages, model policy, trajectory, create/edit requests and the edit route.
- `packages/sdk` — the runtime: a deterministic pure-TypeScript simulation (seeded RNG, event bus, tilemap physics with runtime tile changes for doors, FSM/ECA interpreters, `defineSystem`) plus a Phaser 4 view, manual/realtime drivers, the test seam (`window.__game`, `window.__TEST__`) and the iframe bridge guest.
- `packages/engine` — builds the shared engine chunk (Phaser + SDK) that every game bundle treats as externals; syncs Phaser's agent skills into the harness.
- `packages/validators` — pure checks: level solver (BFS over the feel preset's jump envelope, with air jumps, a dash and exact air speed for ability-gated genres), behaviour structure, GDD front matter and sections, systems against the catalog, juice lint over a playtest event log, parameter impact.
- `packages/template-core` and `packages/templates` — the genre contract (`GenreManifest`), shared systems (pickups, top-down movement, wave spawner, survival timer, arena validators) and the genre packages: `genres/platformer` (Celeste-class feel, chunk-grammar levels, walker/hopper/turret FSMs, walker and chaos bots), `genres/survivors` (top-down arena, auto-attack with level-ups, wave spawner, kiter/afk/chaos bots, DPS-vs-pressure wave validation) `genres/topdown-action` (rooms joined by doors, directional melee with aim assist, telegraphed enemy bites, archers, the exit locked until the floor is clear, a path-finding clearer bot as solver) `genres/shmup` (one-screen sky, waves from the top, hold-to-fire shots, aimed bullets, drones that weave and tanks that grind, a trajectory-scoring dodger bot as solver) and `genres/metroidvania` (one cavern per level with ability gates: wings behind the start for a double jump, a cliff only it clears, a key on a pillar, a locked door that opens at runtime, boots for the dash and a spike pit that needs both; an ability-gated reachability search as validator and a planning seeker bot as solver, while the greedy walker must fail) and `genres/puzzle` (Sokoban-class boards: one tile per step, one crate pushed at a time, free undo and restart; a push-optimal A* solver with dead-cell and 2x2-freeze pruning and a step budget is the validator, boards are generated by reverse play from the solved position and ramp by the fewest pushes they need, and the solver bot plays the plan in the real sim). Adding a genre is one entry in `packages/templates/src/node.ts` and one in `src/check.ts`, plus the package in the templates, game-base and web dependency lists. Each genre also exports a browser-safe check kit (its validator, bots and solver); `@gg/templates/check` collects them so the level editor runs the gate's own check in the page.
- `packages/game-base` — the dependency set every scaffolded game links against, so a game outside the workspace still builds and tests.
- `tools/scaffold` — `gg-scaffold`: emits a complete game package from a GDD, systems.json and style card; every placeholder level passes the validator and the genre's solver bot.
- `packages/bots` — Playwright smoke (ready flag, zero console errors, manual vs realtime vs in-page replay hash), contact sheets, a static server.
- `packages/llm` — provider clients (Anthropic, OpenAI-compatible), pricing, and the sample → verify → repair → select loop for schema-constrained artifacts.
- `packages/db` — the `Store` interface (games, versions, jobs, events, trajectories, policies, objects, remix forks with lineage, and the community layer: plays, one-tag ratings, per-player ranking, publishing to the feed, a rewarded test queue with credits, moderation: player reports, suspension at three reporters, moderator resolutions, takedowns (the bundle files go to a private quarantine) and strikes, appeals and DMCA counter-notices with reinstatement, play events for the creator's heatmaps: deaths, quit points and position samples, aggregated per tile for the owner, training pairs for distillation, never stored for anyone who opted out, and jams: themed events whose entries are frozen at the version entered and whose votes need a play of it) with a Supabase implementation and a JSON file store for local runs. `supabase/migrations/0001_core.sql`, `0003_community.sql`, `0004_moderation.sql`, `0005_play_events.sql`, `0006_appeals.sql`, `0007_training_pairs.sql` and `0008_jams.sql` are the schema; 0004 also limits what a signed-in client can write directly (state, listing, heads, credits and the moderator flag change only through the functions). `ranking.ts` holds the rank formula, the moderation thresholds and the jam rules and standings; the migration test runs the migrations on an embedded Postgres (PGlite) with Supabase's API roles and default grants, checks SQL and TypeScript rank the same rows the same way, and checks the client privileges.
- `packages/catalog` — the style reference feature's boundary: curated cards of unprotectable attributes for named games (palette mood, pixel density, outline rule, animation feel, camera, typography class, audio mood), a resolver for free-text titles, a merge into the style card, and a sanitiser so titles and blocked terms (characters, places, studios) never reach a prompt or a bundle.
- `packages/config` — eslint preset with the GlueTS rules for simulation code, tsconfig presets, the game vite config.
- `samples/platformer` ("First Steps"), `samples/survivors` ("Last Light"), `samples/topdown-action` ("Ember Halls"), `samples/shmup` ("Static Sky"), `samples/metroidvania` ("Undervault") and `samples/puzzle` ("Crate Cellar") — hand-tuned golden games built from the template systems plus data.
- `harness/` — the per-job Claude Code project: `AGENTS.md`, path-scoped rules, subagents, hooks, the worker-runnable gate, per-stage presets (`stages.json`), budgets, and skills with bundled scripts (gdd-author, systems-select, mechanic-author, behaviour-author, level-design, asset-prompting, playtest, juice-pass, regression, budget-check, edit-apply, playbook, verify).
- `workers/generator` — the job state machine: create plan (GDD → systems → scaffold → behaviour → implement → levels → integrate → playtest → juice → review → budget → publish) and edit routes (parameter, style, behaviour, content, code, plus authored content from the level editor, which skips the router and is written only after the validator and the solver bot accept it); runners for Claude Agent SDK sessions, a built-in guarded tool loop for open-weight and OpenAI-compatible models (same AGENTS.md, skills, playbook, path and command guards as code, scrubbed context), structured calls and worker-implemented stages; worker-owned gates, checkpoints, trajectories (every attempt's gate report is kept), the publisher; a fake provider for dry runs without keys. When a job finishes with every gate passed, the model-written artifacts of its stages (GDD front matter and body, systems, behaviour FSMs, structured artifacts, the edit route) become training pairs against the stage's first prompt; fallbacks, dry runs and anyone who opted out (the requester, the game's owner or the owner of a game it was remixed from) are left out.
- `apps/web` — Next.js app: the home page is the ranked feed (listed games whose gates passed and that players have not marked broken); the play page records each session (active seconds, levels finished, deaths, and where the player died, spent time and quit; sent on pagehide) and takes a one-tag rating; the test queue page lets a player claim an unreleased game, play it 30 s, report works or broken and earn credits; players report a game from the play page (ip, abuse, broken, other) and moderators work the `/moderation` queue (dismiss, unlist until fixed, warn, licence an ip claim, remove); a suspended game is hidden from everyone but its owner and moderators, a removed one from everyone, and neither can be remixed. The owner of a removed game appeals from its workspace (a counter-notice with consent to jurisdiction for an ip takedown, which moderators can reinstate 14 days later; a plain appeal otherwise), and moderators reinstate or uphold from the appeals queue. Locally a header switcher sets the acting user (`moderator` is the file store's moderator). Jams (`/jams`): moderators set a theme and when entries open, submissions close and voting closes; owners enter one listed game made after the start (for a remix, its original too), frozen at the version entered; players who played an entry 30 s score it 1-5 on fun, theme and look, never their own; results rank entries with 3+ votes by a score that counts three extra votes of 3 per criterion, and leave out entries taken out of the feed. The create page and the games list carry the player's training consent: unchecking it opts all their games and remixes of them out and deletes what was recorded. Also the create form (with style references), games list, the creator workspace (job progress, playable preview in a sandboxed iframe over the bridge, evidence panel, edit chat, parameter tuning panel, style card editor and a tile/entity level editor that send deterministic edits, remix, and a community panel to publish to the feed and ask for testers; the level editor can overlay other players' deaths, quit points and time spent on each tile), the play page with a remix button. The workspace is the owner's (moderators may look in; anyone else lands on the play page), since its jobs carry prompts, edit messages and private style references; its code view lists a version's source from the checkpoint (systems, levels and behaviour data, design files, tests, config; never the private concept, an edit request, provenance, build output or reports), marks what changed since the version it was built on with a line diff, and "Ask for a change" starts an edit about a file. The level editor checks a level in the browser with the genre's validator and solver bot before it can be applied; dev and build run on webpack so the shared TypeScript packages resolve.
- `tools/evals` — the benchmark: 33 prompts across the six genres, dry or live runs per policy, pass^k and per-stage rates, cost per passing game; policy files for the frontier path, the first cheap experiment (Haiku with k-sampling) and an open-weight policy through the built-in open runner.
- `tools/playbook` — distils playbook candidates from stored trajectories (a stage that failed its gate then passed, with the failing checks and the passing summary); `promote` appends a verified lesson to the genre's playbook with its source.
- `tools/distill` — `pnpm distill status` counts verified pairs per stage against the 2,000 unique inputs a LoRA run needs; `pnpm distill export` writes chat-format `train.jsonl` and `holdout.jsonl` per stage (one pair per input, the split fixed by the input so nothing moves from holdout to train between runs, games under moderation left out) with a manifest of file hashes, pair ids, models and the artifacts' JSON Schemas, and stamps the pairs it exported. Exports hold user prompts and go to the git-ignored `.gg-distill/`.
- `tools/demo` — `pnpm demo` runs the sample through the whole gate, then a dry-run create job through publish, then an authored level edit (a coin on the spawn tile) through apply-content, playtest and publish, and prints the evidence bundle.

## Running it

```
pnpm install
pnpm typecheck && pnpm lint && pnpm test
pnpm demo                       # engine + sample gate + a dry-run create job through publish
pnpm bench --limit 2 --k 1      # one prompt per genre through the pipeline (dry)
pnpm distill status             # verified training pairs per stage (live runs record them; dry runs do not)
pnpm distill export --new-only  # chat-format JSONL per stage in .gg-distill/

# create a game from the CLI (dry run needs no key; drop --dry-run with ANTHROPIC_API_KEY set)
pnpm --filter @gg/worker-generator exec node --import tsx src/cli.ts create --prompt "..." --genre platformer --dry-run
pnpm --filter @gg/worker-generator start -- --once

# apply levels authored outside the model (what the level editor sends): { "levels": [LevelJson, ...] }
pnpm --filter @gg/worker-generator exec node --import tsx src/cli.ts edit <gameId> --message "edited l01" --content levels.json --dry-run

# the web app (reads the same local store; run a worker alongside it)
pnpm --filter @gg/web dev      # http://localhost:3000 (feed), /create, /test (test queue)
```

## Key decisions so far

- Web app first; a desktop wrapper (Tauri) only later for a Steam listing.
- 2D and platformer games only for the first version, with a platformer and a survivors-like as the initial vertical slice.
- Phaser 4 in a thin platform SDK as the fixed runtime; Colyseus for multiplayer; games sandboxed in opaque-origin iframes.
- Named game references resolve to a visible style card of unprotectable attributes; characters, names, logos, layouts and music are blocked.
- Quality must not depend on the model: the model emits data under small schemas and restricted glue code, never engine API calls; every stage samples, verifies, selects and escalates; knowledge is curated from verified runs; a second runner (OpenCode) carries open-weight models.
